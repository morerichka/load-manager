# Security and recovery notes

Load Manager 0.8 is a developer preview. Run it as a normal user and do not grant blanket administrator privileges. Do not use process suspension on calls, active transactions, synchronization, or other important background activity.

The app exposes only snapshot/apply/restore methods to its bundled local page. It has no HTTP mutation API. It never accepts cache paths from the UI, and no shell is ever used. It checks process owner, name, executable path, PID creation time, and relevant ancestry before an action. The app catalogue is a usability boundary, not a code-signature trust database. Chrome, Claude, Telegram and Google Drive are acted on only on Windows, only as a whole group re-enumerated at apply time, and never when they are an ancestor or descendant of Load Manager itself. Group members that vanish or refuse mid-apply are skipped; an explicit single-process selection that fails still rolls everything back.

Recovery uses a write-ahead per-session journal and a separate child process. If Load Manager exits unexpectedly, the guardian attempts restoration. Startup also retries incomplete journals. If the target's identity has changed, it is not touched. If another tool changes a Windows priority, that external change is preserved. Access-denied recovery entries remain available for retry.

POSIX suspension and resumption are OS signals; Windows uses scheduling classes, EcoQoS (SetProcessInformation) and working-set trimming (EmptyWorkingSet). The original EcoQoS state is journaled and restored exactly; an app that already had Efficiency mode on is never taken over. Trimming is not journaled because nothing needs restoring. Helpers started by a lowered parent inherit the lowered class, so the journal also records the original class per app and restore raises such helpers back. While a Render session runs, new ffmpeg or editor processes of the same user are raised above normal and journaled the same way. Load Manager never raises anything to High or Realtime, never needs administrator rights, and never touches other users' processes. Journals cannot coordinate with every other process manager. Avoid simultaneously managing the same processes in another utility. System shutdown, permissions changes, or external process state changes can prevent restoration. This version does not promise recovery from every failure.

Keep journals private. They contain executable paths and process identities, not source code or credentials. When reporting a bug, redact local paths and usernames. Never include access tokens or private project contents in a public issue.

Auto-start (off by default, switch on the Render page) changes process priorities without a click, but only the same changes a manual Render session makes, on the apps you ticked, for as long as a render tool is busy. It never touches a session you started yourself, writes the same recovery journal, and ends when the render has been over for the grace period or the app closes.

The *Time a real command* feature is the one place where the app starts a program on request: the single-line command typed in the Render page, executed directly (no shell, no pipes or redirects) as a child of Load Manager, only after you press a run button, with an optional working folder. The page is bundled and loads no remote content, and the command text is never taken from a process list, a file or a network source. Its output goes to `timed-last.log` in the state folder (overwritten each run). *Cancel*, and closing the window, stop only that command and its children. Do not put secrets on the command line: it is saved in `settings.json` as the last command and in `history.json` with each timed run.

Quiet mode changes the active Windows power plan (powercfg /setactive, no administrator rights needed), only when you press the button, enable *start with the app*, or when a render hands the plan back. powercfg is started directly without a shell and only with a plan id that matches the GUID format. The plan that was active, the plan switched to, and the plan currently set are written to the recovery journal before each change, so the guardian and the next start restore it after a crash; if the original plan no longer exists, or something else changed the plan in the meantime, nothing is forced and the reason is logged. Quiet mode never changes plan settings (processor limits, fan curves), only which plan is active.

The spike recorder reads the name, parent, start time and CPU time of every process, including other users' and system services, from a single read-only system call (NtQuerySystemInformation). It never reads command lines, window titles or files, never touches those processes, and keeps only program names and totals in `history.json` on this device.

The second quiet-mode method changes two settings of the active plan (turbo boost mode and the maximum processor state) with `powercfg /setacvalueindex` and `/setdcvalueindex`; no administrator rights are needed. The old values of exactly those settings are written to the recovery journal before the first change, restored by the guardian after a crash, and each setting is restored only if it still has the value Load Manager gave it. Nothing else in the plan is touched, and plans are never created, edited or deleted by the app itself (the opt-in live test makes and deletes a temporary copy of your plan, and works on that copy only).

While quiet mode is on and work is running, the app holds a Windows power request (`PowerCreateRequest` / `PowerSetRequest`, system required) so the laptop does not sleep on its own; the display may still turn off. The request is cleared a minute after the work ends, when quiet mode ends, and by Windows if the process dies. It can be switched off on the Power page.

The Claude kit (`lm install-claude`) changes `~/.claude/settings.json` and writes a skill and a launcher under `~/.claude/`. The settings file is read as JSON, a backup is made first, only one `PreToolUse` entry that mentions `loadmanager.guard` is added or replaced, every other setting and hook is kept, and a file that is not valid JSON is left untouched with the lines to add by hand shown instead. `lm uninstall-claude` removes only what the installer added.

The hook (`python -m loadmanager.guard`) reads the JSON Claude Code sends (the command text and the working directory), never runs anything, imports only the standard library, and allows the command whenever it cannot understand the input or hits an error. It only ever blocks a media tool aimed at a cloud-synced folder, and `LM_ALLOW_DRIVE=1` in front of a command is the deliberate way around it.

`lm fetch`, `lm publish` and `lm proxies` copy or create files; they write to a part file and rename it when the size matches, never replace a different file without `--force` (publish) and never delete anything. `lm clean` is the only command that deletes: it lists first and deletes only with `--yes`. With `--src` it removes only local copies that `lm fetch` recorded, whose original is still in the cloud with the same size and whose own size still matches that record (anything else is listed as "keep"); with `--proxy` it removes proxy files, which can be made again. It skips symlinks and never touches `out/`. `lm run` starts the command you give it directly (no shell) and only keeps the computer awake around it.

The Video page runs the `lm` commands for the window. Each job is a child process of the app, started with an argument list and no shell; every path from a form must be absolute (so it can never be read as an option) and is passed after `--`; preset, codec, bitrate and project names are checked against fixed patterns; "extra ffmpeg arguments" and "Run a command" are split like a shell would split them but are never run through one, and they are the one place where you can pass anything you like to a program, as you could in a terminal. A job gets `LM_*` settings from the Video page only: any `LM_ALLOW_DRIVE` or other `LM_*`/`VK_*` variable of the shell that started the app is removed, so the cloud-folder guard cannot be switched off from outside. Cancel is a file the job watches (it acts like Ctrl+C); a job that ignores it for 12 seconds is stopped with its child programs. "Show in folder" only shows a folder or selects a file in Explorer/Finder and never opens a file. The deleting `lm clean --yes` is only started from a second, separate button after a preview with the same choices. File dialogs are the system ones; no path is sent anywhere. Settings of the page (work folder, encoder, spare space, ffmpeg path) are stored in the app's own settings file next to the other preferences.

The queue keeps the form values of waiting items (paths, command text) in the app's own history file next to the other preferences, and restores them paused. An item is checked again, with the real files, when its turn comes, and goes through the same rules as a job started by hand.

"When everything is done" can put the computer to sleep, hibernate it or shut it down (`SetSuspendState` / `shutdown /h` / `shutdown /s /t 10` on Windows, `pmset sleepnow` / System Events on a Mac, `systemctl` elsewhere; shutting down does not force programs closed). It can only be armed in the window, for one time; it is never written to disk and is forgotten when it has happened, when it is cancelled, and when the app restarts. It starts a 60-second countdown that is shown in the window and in a notification and can be cancelled, it is stopped by any new job, and it never runs after a job you cancelled yourself. The tests replace the power call, and the code refuses to power anything off when it runs under pytest, so a test cannot sleep or shut down the machine it runs on.
