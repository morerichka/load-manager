# Validation: Load Manager 0.8.0 (29 October 2026)

Run on Windows 11, Python 3.11.9, psutil 7.2.2, 24 logical CPU threads.

## What was verified

- Python engine and launcher: **514 passed, 8 skipped** (the POSIX parent-crash test and the opt-in live tests below, which are run separately). Seven deliberate regressions were injected into a copy of the engine (no inherited-helper sweep, no render boost, trim ignoring memory pressure, taking over an existing EcoQoS state, heavy apps allowed off Windows, lowering Claude, aborting on a vanished tab); each one made at least one test fail.
- **Real Windows mechanisms**, `tests/test_windows_live.py` (opt-in, `LOADMANAGER_LIVE=1`): 24 CPU burners, plus a parent that starts a child mid-session and an `ffmpeg.exe` copy, all disposable copies of `cmd.exe`. Verified on the real OS: EcoQoS read/set/restore round-trip with the exact original masks, idle priority, working-set trim (about 260 MB freed from 25 small processes), a child created by a lowered parent inheriting the idle class and being swept back on restore, the render tool lifted to above-normal and put back, an empty journal at the end.
- **Measured effect on this machine** (built-in probe, MiB/s of multi-threaded hashing at normal priority):

  | Situation | Score |
  |---|---|
  | quiet machine | ≈30 700 |
  | 24 background burners at normal priority | ≈12 800 (−58%) |
  | same burners at idle priority + EcoQoS (Load Manager session) | ≈30 000 (+134% vs. loaded) |

  This is a **synthetic** load made of CPU-bound processes. It proves the mechanism and the measurement, not a specific speedup of a lesson render.
- Read-only `--snapshot` on this PC found 17 Chrome processes (≈2.0 GB), 18 Claude processes (≈3.5 GB, two of them correctly protected as Load Manager's ancestors), 1 Telegram process (≈640 MB), and RAM use of 71.7%. Google Drive was not running. Nothing on this PC was changed: the real Chrome, Claude and Telegram were not touched.
- Interface: jsdom behaviour checks pass (`npm run test:dom`), including heavy-app groups, the one-click editing mode, the benchmark panel, macOS protection and the exact bridge calls made in the native shell. The Playwright run (`npm test`, executed with the installed Chrome) passes, including the 390 px phone layout of every page.

## Added in 0.3: auto-start and the timed command

- Unit tests (44 new): the auto-start state machine driven with explicit time (start delay, grace period, gap between two ffmpeg calls, manual sessions left alone, a session ended by hand not restarted, back-off after a failed start, trim-only results not repeating, pause, persistence, validation) and the timed run (order, failure, crash, cancel, concurrency, input validation, real commands with exit code and output).
- Live on Windows 11 (`LOADMANAGER_LIVE=1`): a real timed A/B with 24 busy look-alike apps: **6.1 s without a session, 3.0 s with one (51% saved)**; an earlier run of the same test saved 21%, so expect noise. Auto-start followed a real `ffmpeg.exe` look-alike: session started within about 6 s of it burning CPU and ended after it exited.
- A real lesson render has still not been timed.

## Added in 0.4: spike log and quiet mode

- The monitor itself was the first thing found to heat the laptop: one tick cost about **1.8 s of CPU every 2 s** (asking about ~400 processes one by one is quadratic on Windows). It now reads all processes in one system call and costs about **0.12 s** per tick. A regression test fails if a tick exceeds 0.5 s of CPU.
- Unit tests (53 new): power plan parsing in two display languages, no-shell switching and ID validation, journaled entry and return, crash recovery by the guardian (also when the process dies in the middle of a switch), plans changed by someone else, a deleted original plan, render phases on the original/chosen plan (Render session, auto-start, timed A/B), nothing forced on failure; the recorder's state machine (start delay, minimum length, hysteresis, gaps), attribution (via Claude, via Load Manager, reused PIDs, loops), thresholds, persistence, ranking across periods, and the one-call process table (CPU maths, PID reuse). Sixteen deliberate regressions were injected; the first run left four alive, the tests were tightened, and all sixteen are now caught.
- Live on Windows 11: the process table reads 372 processes in about 8 ms and sees system services (`bdservicehost.exe`, `svchost.exe`, `SearchIndexer.exe`); per-process CPU adds up to 6.5% against 7.7% for the whole machine. A real busy period was recorded from four busy look-alike apps: 16.7 s, average 24.9%, top culprit named with 4 processes and 58.8% of the CPU time.
- After the 0.4 changes only the gentle live tests were rerun (auto-start following a real `ffmpeg.exe` look-alike, and the recorder). The heavy ones that saturate all 24 threads for a minute or more (the 24-burner benchmark and timed A/B) were not, to spare the laptop; their code path is covered by the unit tests with doubles.
- **Quiet mode on the real power plans (run on this laptop, with permission):** the opt-in test switched Turbo → Silent, confirmed Windows reported Silent, returned to Turbo, switched again, and the guardian's recovery from the journal put Turbo back; it took 3 s and the laptop ended on Turbo. A second round trip watched for 14 s: Silent stayed selected (13 readings), Armoury Crate did not switch it back, and quiet mode stayed active until it was left.
- **What the Silent plan really changes** (read-only comparison of all 60 settings against Turbo): minimum processor state 80% instead of 100%, display brightness 76% instead of 91%, **sleep and display-off after 5 minutes instead of 30**, PCIe link power saving on, and wireless power saving on battery. Maximum processor state and boost are identical in both plans. So the plan switch alone lets the CPU idle lower, but whether the fans get quieter depends on whether the ASUS fan profile follows; that cannot be measured from software here and is untested. The shorter sleep timeout is a real side effect: a long unattended job may be interrupted by sleep after 5 idle minutes while quiet mode is on, unless the program holds a wake request.
- `powercfg` output on this laptop (plans Performance, Balanced, Silent, Turbo, PD Performance) parses correctly in the app and Silent is picked as the quiet plan.

## Added in 0.5: keep awake, and the processor-limit method of quiet mode

- Unit tests (50 new): both methods side by side, never raising a lower value that was already there (mains and battery separately), settings the plan lacks, half-applied and refused changes undone, a crash in the middle of changing, the guardian's recovery, a setting or plan changed by someone else, a deleted plan, partly failed returns retried for the rest only, render phases and a timed A/B on the same settings, the hidden-settings query read by position in two languages and strict argument checks, and the keep-awake rules (only in quiet mode, every sign of work, one request not one per tick, a minute of grace, released on leave/close/outside change, switch, refused request retried). Eleven more deliberate regressions were injected: one survived at first (the mains value could be raised), a test was added, and all are now caught.
- **Which processor setting works on this laptop** (one busy thread, on a temporary copy of the active plan, nothing else changed; busiest core as % of base clock, one-thread hashing speed): nothing changed 246% / 2314 MiB/s; maximum processor state 100 → 50: 246% / 2292; maximum frequency 2500 MHz: 248% / 2319; energy preference 100: 252% / 2224; boost policy 0: 253% / 2299; boost modes Enabled, Efficient Enabled, Efficient Aggressive, Aggressive At Guaranteed and its efficient variant: 252% each; **boost mode Disabled: 101% / 921 MiB/s** (about 60% slower on one thread, the clock at the base). Only turning boost off did anything, so that is the main setting of the limit method; the maximum state stays available for processors that honour it.
- **The limit method through the app's own code** (opt-in test, on a temporary copy of the plan in use, deleted afterwards; the real plans were never edited): boost turned off, the busiest core 243% → 101%, one busy thread 2308 → 919 MiB/s, everything restored on leaving, and restored again from the journal by the guardian after a simulated crash. A real Windows power request was created, held and cleared. The laptop ended on Turbo with its five plans unchanged. The process list cannot show the request without administrator rights (`powercfg /requests` needs them), and the laptop was not left idle to watch it actually stay awake.
- The change in fan noise cannot be measured from software here; turning boost off clearly lowers the clock, which lowers heat and fan demand, but how much quieter it is for your work is for your ears and the Spikes page.

## Added in 0.6: one tool for Windows and Mac (the Mac Video Kit merged in, in Python)

- 176 more automated checks than 0.5: cloud-folder detection on both systems (Windows letters, `Мой диск`, `iCloudDrive`, macOS `CloudStorage`), the hook (compound commands, quoted `.exe` paths, working directory, query flags, `cd` away, the escape hatch, unreadable input always allowed, no heavy imports), fetch / publish / clean / status with a stand-in ffmpeg (copy with part files, retries, skip, refuse, safe cleanup including every reason to keep a copy, symlinks), encode planning with the flags for each hardware encoder, hardware choice by self-test per system, stay-awake and notification paths for each system (fakes), proxies (resume, bad clip, name collisions, one hardware decision per batch), the settings.json merge (other hooks and keys kept, backup, invalid JSON left alone, twice is harmless, uninstall exact), and the bootstrap kit mode. Deliberate regressions were injected into the hook, cloud detection, video and installer code on copies; one survived at first (a clip that cannot even be started stopping the whole proxy batch), a test was added for it, and all injected regressions are now caught.
- **Real ffmpeg on this laptop** (8 checks in `tests/test_video_real_ffmpeg.py`, using the ffmpeg 6.1.1 that the `deutsch-dialoge` project carries; ffmpeg is not on this laptop's PATH, so `lm doctor` here says so until `winget install ffmpeg`): the doctor self-tests the encoders: NVIDIA NVENC and AMD AMF (h264 and hevc) pass, Intel QuickSync fails as expected (no Intel GPU), libx264 and libx265 are present. Real encodes through the app's own command lines decoded without errors: software proxy (720p h264 with audio), software final, the hardware proxy / fast h264 / fast hevc (the checks use whatever the self-test picks first, here NVENC), and a two-clip proxy batch that a rerun skipped.
- **The hook as Claude Code runs it:** the command written into a temporary `settings.json` was executed through a real shell with Claude's JSON on stdin; it blocked a media tool aimed at `G:\My Drive\...` with exit code 2 and the instructions, allowed a local command silently, and allowed garbage input.
- The real `~/.claude/settings.json` of this computer was not touched: install and uninstall were run against a temporary folder only.
- **Not verified, no Mac was available:** the VideoToolbox encoder flags and `-hwaccel videotoolbox`, `caffeinate -w`, `pmset`, `sw_vers`, `osascript` notifications, running the installer from `INSTALL-Claude-Kit.command`, Python 3.11 from python.org or Homebrew on a Mac. The Mac flags are the ones of the shell kit this replaces (which was itself not run on a Mac). The first thing a Mac user should do is run `lm doctor` and `python3 -m pytest` (or send back the output of `lm doctor`). On Windows, QuickSync was never exercised (no Intel GPU) and the balloon notification was not displayed.

## Added in 0.8: the queue and "when everything is done"

- 42 more automated checks (514 passed in all), `tests/test_video_queue.py`, with real jobs as child processes against the stand-in ffmpeg: buttons pressed during a job wait and run in order; an item may wait for a file an earlier item makes; a wrong form is refused when added; an item whose file never appears fails when its turn comes and stops the queue (or not, with "Keep going"); a failed job pauses the queue by default; cancelling pauses it and keeps the rest; pausing while idle lets a plan build up; moves, removals, clearing and the size limit; the waiting items survive a restart, paused, and damaged saved items are ignored one by one; closing the window starts nothing new; twelve buttons pressed during the hand-over between two jobs lose and double nothing (taking the next item and starting it is one step). The action after the last job: sleep, hibernate and shut down each fire once after a warning and a notification; it waits for the whole queue; it never fires after a job you cancelled, or after a cancel that left the queue paused, but does after a failure that stopped the queue; a new job stops the countdown and keeps the choice, and the old timer cannot fire the new countdown; cancelling or choosing "nothing" forgets it; a refusal by the computer is shown, not raised; it is one-shot; the choices depend on the system. The real command lines are checked for every system with a fake runner, including failures. The bridge answers for every queue call in the shapes of `tests/video_contract.json`.
- `tests/dom_video.cjs` now also covers the queue (buttons that say "Add to queue", reorder, remove, pause and resume, keep going, the choice for the end, the countdown banner and its cancel, the Mac list of choices, a job replaced between two looks still announced) in the demo and against the contract, stable over repeated runs; `tests/ui.cjs` (real Chrome) checks the queue panel and the countdown at 390, 760 and 1440 px.
- 22 deliberate regressions in the queue code (a paused queue starting, a cancel carrying on and counting down, a pause by you counting as finished, the action not being one-shot, new work not stopping the countdown, a queued item having to find its file at once, the failure policy inverted, up and down swapped, a restored queue starting by itself, an unstartable item recorded as done, hibernate shutting down, any choice accepted, last-in-first-out, an old timer firing the new countdown, no time to cancel, no limit, buttons never queuing, things that cannot wait being queued, no paused flag in the summary): all caught.
- **The real page, the real backend and the real ffmpeg** (the one-off end-to-end script from 0.7, extended): a second encode pressed while the first ran waited and ran after it, both files were made, the countdown appeared only after both, and "sleep" was requested exactly once afterwards (the bridge's power call was replaced by one that writes a file).
- **Not verified:** the computer actually going to sleep, hibernating or shutting down on any machine. It could not be tried without switching off the computer the work was done on. On this laptop (Modern Standby plus hibernation, per `powercfg /a`) Windows' sleep call may behave differently from the Start menu's sleep, and if so the Hibernate choice is the reliable one. Also not verified: `pmset`, System Events and `systemctl` on real systems.

## What was not verified

- Opening the native pywebview window, `START-Windows.cmd`, the desktop shortcut and PyInstaller bundles were not run.
- macOS: the new code leaves the Mac behaviour unchanged (light apps, pause) and was only exercised through mocks.
- Google Drive (`GoogleDriveFS.exe`) was not running, so that process name has only been checked in the catalogue; if your Drive client uses a different executable name, add it to `APPS["gdrive"]["names"]` in `loadmanager/engine.py`.
- No real lesson render has been timed. Use the CPU benchmark panel or time the render with and without a session.
- Disk and GPU limits are not measured by the probe.
